## Contract before implementation

Loom must refuse a dispatch whose conservative projection would exceed any
applicable goal or cycle ceiling, and latch a durable halt before returning a
paused outcome. It must check before the next invoke, including retries and
fallbacks inside one gateway request. Halting stops new work immediately at the
admission boundary; it requests cancellation of work already admitted and still
accounts for its eventual or uncertain spend. It cannot undo an external effect
or an invoice already incurred.

Policy is deterministic. Model answers remain observations and cannot change a
ceiling, clear a halt, mint authority or lower required quality. Under local
ceiling pressure, audit and work requiring `strong` pause rather than weaken.
Whether that also removes HEAD's quota-driven ahead-pace strong-to-standard
downgrade is open fork P6; until P6 is answered this contract makes no claim
about that existing exception. D4/D7, disclosure, admission and
execution grants remain independent gates. A cheaper route is optional and may
be considered only before a hard halt, within unchanged authorized terms.

The acceptance boundary is zero overshoot of **reserved projected resources**
under the declared upper bounds. Actual external charges can exceed a provider's
declared bound; that limitation must remain explicit, with conservative retained
liability and no further dispatch. This is not a promise of exactly-once provider
billing or instantaneous termination of an uncooperative process.

Defaults. Enforcement scope is product fork P1. On an enforced goal, cost and token
ceilings must be explicit at first; there is no derived cost or token default.
Cycle cost/token sublimits inherit the remaining goal allowance unless explicitly
tighter. Zero permits no corresponding work. Project/operator policy may tighten
any ceiling; raising one requires the entitled principal and a durable policy
amendment. Retries/resumes do not replenish spent resources. Do not enable a
partially configured switch silently.

Count defaults are derived from existing caps so that a cycle staying inside
today's bounded loops cannot trip them. Let `a` be a request's `max_attempts`
(runtime weigh terms use 3), `R` = `DEFAULT_IMPLEMENT_RETRIES` (2), `c` = check
invokes per implementation attempt, `M` = audit `max_iterations` (default 4) and
`o` = paid `observe` invokes per audit round. Worst case for a cycle that weighs
once, dispatches one host action, runs one implementation step and one audit loop:

- invokes = weigh `a` + host dispatch `1` + implementation `(R + 2)(2a + c)` +
  audit `M(3a + o)`. Implementation counts the initial attempt, retries and one
  escalation, each generating, checking and running D5; audit counts D6,
  generation and D8 per round;
- requests = `1 + 2(R + 2) + 3M`; edges = gateway retry/fallback `(a - 1)` per
  request + implementation retry/escalation `R + 1` + audit loop-back `M - 1` +
  cycle entry `1`.

With `a = 3`, `R = 2`, `c = 1`, `M = 4`, `o = 0`: invokes = 3 + 1 + 28 + 36 = 68;
requests = 21; edges = 42 + 3 + 3 + 1 = 49. The earlier 16-invoke and 8-edge cycle
figures are below one legitimate cycle and are withdrawn. Recommendation for P2:
compute cycle invoke and edge defaults at goal admission from the effective caps
of the largest composition the goal's policy admits in one cycle (summing per
admitted step when a cycle may run several), record the inputs, and set goal
defaults to cycle defaults times an approved cycle allowance (recommend 4: 272
invokes, 196 edges for the values above). These are derivations, not existing
constants or measured safe values.

Reuse `BudgetLine` arithmetic and existing request reservations where possible,
and `impl.attempt@1`, `impl.stop@1`, `audit.round@1` for their existing meanings.
Include slice assembly once in the existing goal cost total; retain a
provider-cost subtotal for this feature.

Request envelope transfer (decided, architectural). At HEAD, `applyAccepted` on
`inference.recorded` releases the whole `request.reservation` and adds the
payload's `spent`, and `abandonUnrecordedInferences` records `spent` equal to
`reservation.cost`. Both would double-charge or drop liability once per-attempt
settlements exist, so enforced requests use a new version:

- An enforced gateway request opens with `inference.requested` at
  `payload_version:2`. Version 1 keeps HEAD's fold exactly and is refused on an
  enforced goal. Version 2 adds `accounting: { goal_id, cycle_no,
  policy_revision, envelope }`, where `envelope` holds cost micros and token,
  invoke and edge bounds; `reservation.cost` equals `envelope.cost`.
  `validation.ts` currently rejects every `payload_version !== 1`; C1 admits
  version 2 for these two payload types only, and `weft.ts` projects both versions.
- Each provider-attempt `budget.reserved` names `envelope_request_id` and
  `allocation_id` and transfers its amounts from the envelope's unallocated
  remainder. A transfer moves liability within `reserved`, so goal and cycle
  totals do not change. The fold keeps per envelope `unallocated`, the open
  allocations and the settled sum.
- `budget.settled` for an allocation of `x` with measured or bound amount `m`:
  `reserved -= x`, `spent += m`, once per allocation.
- `inference.recorded@2` (outer completion): `reserved -= unallocated` and nothing
  is added to `spent`. Its `spent` must equal the envelope's settled sum or it is
  rejected. Its `unresolved` field lists open allocation ids; they stay reserved
  as unresolved liability and remain settleable once. Judgment arithmetic is
  unchanged from version 1.
- Abandonment at recovery of a version 2 envelope releases `unallocated` (an
  allocation is durable before adapter entry, so no allocation means no
  dispatch), keeps settled spend, and leaves open allocations reserved and marked
  unresolved at their bound. It never charges `reservation.cost` again. Version 1
  envelopes keep HEAD's whole-reservation charge.

Token evidence on `InferenceAttemptRecord` is carried only in version 2, with
explicit validation, so version 1 replay is unchanged.

Record versions (decided, architectural). `budget.policy@1` and `BudgetReason`
stay quota policy only; no local-ceiling reason is added to them, and existing
pause records stay readable unchanged. `LoopPausedRecord` becomes a union
discriminated on `policy`: the `budget.policy@1` variant is unchanged, and a new
`limit.policy@1` variant carries a closed `LimitReason` and `until:null`. The
gateway emits that variant through `persist_pause` only when a local ceiling
refuses at the gateway boundary, after the account has appended the authoritative
`budget.halted`. Halts at runtime boundaries append `budget.halted` only, never
`loop.paused`, and surface as specified in Halt outcomes at runtime boundaries.
Rationale: this satisfies the issue's "hard ceiling → `loop.paused` / terminal
stop with reason" mapping without giving quota records a second meaning. Readers
that switch on `policy` must reject an unknown variant, never treat it as a quota
reset. New enforced records require complete evidence; historical logs replay
under historical versions without fabricated zero usage.

Halt outcomes at runtime boundaries (decided, architectural). `GoalStatus` stays
`active | complete | missed`; no goal status is added. A `paused` halt leaves the
goal `active` with a latched halt. A `stopped` halt also appends the existing
`goal.missed` (runtime source is already permitted for it), so the goal becomes
`missed`. The operator-visible projection is a folded `State.limit.halt`
(`halt_id`, reason, dimensions, disposition and evidence seq, or `null`), exposed
through `Runtime.state()` without secrets; Weft may project it but is not
authoritative. Per boundary:

- Cycle entry. If a halt is latched, or the entry edge would exceed a ceiling,
  `runCycleOnce` appends `budget.halted` (boundary `cycle_entry`, `cycle_no:null`)
  only when none is latched yet, appends neither `cycle.opened` nor
  `inference.requested`, records an in-memory
  `CycleRecord` with no selection and outcome
  `{ status: 'blocked', reason: 'limit.policy@1: <reason>' }`, and does not set
  `reuseFollowUp`. Later triggers append nothing.
- Direct host dispatch (`Runtime.dispatch`). Refusal happens before
  `action.started` / `action.queued`, so no action exists and the host is never
  called. `dispatch` returns `null`, as it does when `stillAuthorized` fails, the
  candidate is left out of `CycleRecord.selected`, and the cycle outcome is
  blocked with the limit reason. Siblings already started are unaffected.
- Queued host start (`drainQueue`). A paused halt leaves the action `pending` and
  unstarted, appends nothing per drain and keeps its action/judgment
  reservations; resume reruns `drainQueue`, which reserves again. A stopped halt
  cancels pending work through the existing `action.cancel_requested` path (the
  stale-authority pattern in `drainQueue`) with reason `limit.policy@1: <reason>`,
  which releases those reservations.
- Implementation and audit boundaries additionally surface through the existing
  `budget` outcomes of `impl.stop@1` and `audit.round@1`.

Disposition per reason (recommended; product fork P4 may change the mapping, not
the schema):

| -------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------- |
| `goal_cost_ceiling`, `cycle_cost_ceiling`, `token_ceiling`, `invoke_ceiling`, `loop_depth_ceiling` | `paused`, `until:null` | Resume authorization, plus a ceiling amendment when the exhausted dimension must grow |

## Minimal enforcement points

Execution model (decided, architectural). The runtime stays synchronous and the
account follows it; no second concurrency model is added.

- The gateway-facing port is `allocate(request): Promise<Allocation>` plus
  `settle(...)`, so the gateway stays asynchronous and Loom-free.
- The runtime-side adapter decides synchronously inside the existing
  `Runtime.step`: one `allocateStep` rechecks the halt latch, reads goal and cycle
  counters together, and appends one `budget.reserved` (or `budget.halted`) through
  the synchronous `persist` before the promise resolves. There is no `await`
  inside the decision, so synchronous run-to-completion is the single admission
  queue (`Runtime.step` itself only brackets the step for Weft; it does not queue). That is what "one owner atomically checks both goal and cycle"
  means.
- `persist` stays synchronous inside the critical section. C2's append-and-sync
  upgrade must also be synchronous; an asynchronous journal would need a named
  admission queue and is out of scope.
- `allocate` never decides inside another step. The adapter defers each call to
  its own top-level `allocateStep` on a microtask. A gateway that requests an
  allocation synchronously during the cycle step (before its first `await`)
  therefore gets records after that step's records, never between them.
  `allocateStep` refuses with `accounting_unavailable` if it finds
  `transitionLock` set.
- After the promise resolves, the gateway rechecks cancellation and deadline. If
  either fails, it settles the allocation as proven unstarted through another
  step, durably, before any retry.

Accounting records and replay (decided, architectural). At HEAD, `replay` skips
`runtime` and `judgment` observations (`CYCLE_APPENDED`) because re-execution
must regenerate them, and feeds every other observation in `seq` order through
`feed`. The gateway is never called in replay: `weighAndSelect` skips
`startGatewayWeigh` and framing returns before `gateway.generate`. Records from
gateway allocation and settlement callbacks therefore cannot be `runtime`. Origin
rule:

- Gateway allocations, settlements and gateway-boundary halts are admitted with
  source kind `gateway` (provenance id `loom-account`). Replay feeds them at their
  recorded `seq` and re-validates each against the fold: the reservation fits its
  envelope and ceilings, a settlement cites an open allocation, and a halt matches
  the latched projection. Recorded order and validation are reproduced
  byte-for-byte without calling the allocation port, providers, clocks or timers.
  A mismatch is a `ReplayFailureError`, never a reason to decide again.
- `budget.*` payloads never trigger `runCycle` or `drainQueue`. The exemption is
  by payload type in `admitStep`, so live arrival and replay `feed` behave
  identically. They also join `WEIGH_CONTROL_RECORDS`, so accounting is not new
  evidence for a deferred weighing.
- Runtime-boundary records (`cycle.opened`, non-interrupted `cycle.closed`,
  cycle-entry and direct-dispatch reservations, and their halts) stay `runtime`. The replayed cycle regenerates
  them from the latch and counters folded from earlier fed records.
- Runtime records that no cycle regenerates (queued starts, recovery) follow the
  two protocols below. Every runtime- or judgment-sourced payload type must have
  exactly one declared replay path: regenerated by a named code path, or fed
  under a named exemption.

Queued-start replay (decided, architectural). At HEAD `drainQueue` returns at
once in replay mode, so replay skips a drained `action.started` (runtime source)
and nothing regenerates it; a log with a queued start under finite
`executionSlots` cannot replay at HEAD. C4 replaces that early return:

- Drain points depend only on the accepted record sequence. `drainQueue` runs
  after a cycle triggered in `admitStep` (as now), after every accepted
  `action.result` or `action.reconciled` whatever its source or admitting path,
  after `recovery.closed`, and at the end of `reconcileStep` when no accounting
  port is injected (as now); never while a recovery epoch is open. One
  post-admission hook, run at the end of the step that accepted the record,
  replaces the direct calls in `recordResult` and `recordReconciledStep`. Live,
  a host result reaches `admitStep` through `hostIngress` and then drains again
  in `recordResult`; replay `feed` reaches only `admitStep`. The hook gives both
  modes the same drain points.
- Replay runs the same `drainQueue`. Its inputs are folded state only: pending
  actions in `action_id` order, the running count against `executionSlots`,
  `stillAuthorized` (which already skips `host.canonicalResource` in replay), the
  halt latch and goal/cycle counters folded from earlier records. It regenerates
  in recorded order the runtime-sourced `budget.reserved`, `action.started`, a
  first `budget.halted`, and stale-authority or stopped-halt
  `action.cancel_requested`, and checks them byte-for-byte through `checkPrefix`.
  `replayEnvironment.execute` returns `null` for host operations, so the host is
  never called. The start carries the queued record's grant, a JSON copy that
  replay never issues, consumes or reuses.
- `executionSlots` changes admission, so it is replay input. With an accounting
  port, `cycle.opened` binds `execution_slots`; replay with different options
  fails with `ReplayFailureError` rather than deciding under another capacity.
- Replay's end check treats a `pending` action as finished only when it has no
  `action.started` and `State.limit.halt` is latched `paused`. Any other pending
  or running action still fails as missing a result.
- Compatibility: a drain that appended nothing live appends nothing in replay
  from the same folded state; a drain that appended something made the log
  unreplayable at HEAD. Logs that replay at HEAD therefore replay unchanged. The
  hook adds no live drain where HEAD had none, assuming every live host result
  enters through `recordResult`; C4 verifies that with the existing runtime and
  replay suites, and a divergence is a red test to resolve.

Recovery epochs in replay (decided, architectural). At HEAD `recover` loads the
log and calls `reconcile`, which appends runtime-sourced `recovery.attempted`,
`recovery.exhausted` and lookup-failure `action.result` records, calls
`host.lookup` and drains. `replay` never calls `reconcile` and skips runtime
records, so a recovered log whose `reconcile` appended anything does not replay
at HEAD. The only replay-after-recover test, h1.test.ts `H1-T07 rejects a
duplicate after recover loads the log`, recovers with nothing in flight.
Interrupted `cycle.closed` records would inherit that gap. With an accounting
port, recovery is a recorded, non-executing epoch:

- `reconcileStep` appends `recovery.opened` (`payload_version:1`, source
  `runtime`, `{ epoch }` numbered from the logged count). It then appends one
  `cycle.closed` with outcome `interrupted` per cycle that has `cycle.opened` and
  no `cycle.closed`, each listing the allocation ids and host reservations it
  still owns. Then come HEAD's abandonment, lookups and recovery records, then
  `recovery.closed` (`{ epoch, interrupted_cycles, retained_allocations }`), then
  the post-`recovery.closed` drain.
- The open epoch is folded state (`State.recovery.open_epoch`). While it is open,
  admitted arrivals trigger neither `runCycle` nor `drainQueue` in either mode.
  At HEAD the abandonment `inference.recorded` enters through `gatewayIngress`
  and can trigger a cycle mid-reconcile; under the port it cannot, so recovery
  admits no new goal work and consumes no cycle-entry edge.
- Replay feeds every record from `recovery.opened` through `recovery.closed` at
  its recorded seq, runtime-sourced ones included. The exemption has the shape of
  `feedReviewResult`, keyed on the folded open epoch rather than payload type
  alone. Replay never calls `reconcile`, `host.lookup`, the gateway, the
  allocation port or a grant issuer. Fed records are validated against the fold,
  never re-decided: an interrupted closure must name a cycle opened and not
  closed and list exactly the open allocations and host reservations it owns;
  `recovery.attempted` must name an unfinished action within the recovery
  allowance; a runtime-sourced `action.result` must be `uncertain` for a running
  action; `recovery.closed` is rejected while any cycle stays opened and unclosed
  or when its lists differ from the fold. A mismatch is a `ReplayFailureError`.
- A recovery that itself crashes leaves its epoch open. The next `reconcile`
  opens epoch n+1 directly; the torn epoch's records stay fed and validated, and
  cycles it did not close are closed in n+1.
- Without an accounting port, `reconcile` and replay keep HEAD behavior.
  Recommendation (code health): adopt epochs for every runtime in a separate
  follow-up. It closes the same gap for host recovery but changes the traces of
  existing recovered runtimes, so it does not belong in this feature.

1. At `Runtime.runCycleOnce`, admit/persist the cycle and its continuation edge
   before weighing, framing or any other paid work. Latch checking prevents the
   `reuseFollowUp` loop from spinning after exhaustion. This is an early guard,
   not the sole enforcement point.
2. At `Runtime.dispatch` and queued-start `drainQueue` / `invokeHost`, recheck the
   current halt/policy and reserve the next host invocation before execution.
   A selection made against an older state is not permission to spend. Preserve
   independent execution; serialize only admission and settlement mutations.
3. In gateway `runBoundedLoop`, after quota/routing/pacing waits and immediately
   before `attemptBeforeDeadline`, acquire a bounded allocation through the
   injected, provider-independent port above. Recheck cancellation and deadline
   after it resolves. Persist before calling the adapter; settle even
   failed/unaccepted attempts before any retry/fallback. A wrapper only around
   `generate`/`evaluate` misses the Nth internal attempt.

The runtime-facing adapter owns goal/cycle bookkeeping. Gateway receives opaque
allocation identity, amounts and allow/refuse results; it must not import Loom
state, scheduling or Fabric. The reducer/routing computations remain pure; disk,
locking, clocks, transport and credential access stay behind explicit ports.
Do not put Loom budget policy in Fabric. Host-owned nested execution may enforce
generic finite suballocations without learning what a Loom goal or cycle is.

Wire `runImplementationStep` generation, check invokes and D5 through these boundaries,
and `runAuditLoop` generation, D6/D8 and observation-owned fixes through the same
account. Their existing budget callbacks provide early pause checks, not a
second independent counter. Read-only bookkeeping, terminal settlement and
authorized reconciliation must remain possible after halt; they cannot launch
ordinary goal work or spend an unreserved reconciliation allowance.

For a ceiling L, equality may consume the last permitted unit; a proposed
projection > L is denied. Once spent reaches L, latch a halt for that dimension
before any further consuming invoke. A denied reservation changes neither spent
nor invoke count. With `max_invokes = N-1`, the Nth invoke never enters the host
or provider. Once latched, reducing a projection or finding a cheaper unit does
not automatically clear the halt.

Without an injected accounting port the runtime and gateway are inert with
respect to this feature: no `cycle.*`, `budget.*` or version 2 inference
observations, unchanged traces, digests and replay, and every existing goal and
runtime test unchanged. Only C6 injects the port in trusted composition.

## Failure, cancellation, concurrency and recovery

| Case                                                                 | Required behavior and deterministic evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Concurrent invokes race the last allowance                           | One `allocateStep` inside `Runtime.step` checks both goal and cycle and appends the reservation before the next step runs. With L units and R already reserved/spent, winners reserve at most L-R; losers halt without dispatch. This gives zero projected overshoot across multiple gateway instances within the single owning process. A second process without proven exclusive ownership refuses before calling providers; cross-process coordination is not supported. Best-effort file-size checks alone do not suffice.                 |
| Work already in flight when another call trips the switch            | No new admissions after the halt linearization point. At most K previously reserved invokes remain, where K is the number of live allocations (bounded by the invoke ceiling and configured concurrency). If actual spend A_i respects reservation R_i, actual overshoot is zero; otherwise excess is bounded only by sum(max(0, A_i-R_i)) for those K calls. Without enforceable provider bounds there is no finite invoice guarantee; retain/report the excess and pause.                                                                    |
| Crash before reservation / after reservation before start            | Before durable reservation, no external call. After reservation, keep its complete liability on recovery; do not assume the call never started. Reconcile if supported, otherwise retain the bound and require explicit continuation authority. A conservative false halt is preferable to lost spend.                                                                                                                                                                                                                                         |
| Crash after spend before settlement or counter journaling            | Durable reservation survives and covers the lost result. Recover it as unresolved, retaining bound tokens/cost/invoke/depth. Never resend merely because the request ID repeats. Reconciliation can replace the bound with measured evidence once; absent provider evidence, keep the bound.                                                                                                                                                                                                                                                   |
| Crash mid-cycle; overlapping cycles with late results                | `cycle.opened` without `cycle.closed` is closed as `interrupted` inside a recorded recovery epoch; its counters and owned reservations stay, and it is never reopened or re-allowed. Replay feeds and validates that closure without calling reconciliation ports. A closed cycle is left as is on recovery. A later cycle may open while earlier gateway or host work is outstanding; each late settlement folds into the `cycle_no` it carries, so the current cycle's sublimits are unaffected and the goal total is charged once.          |
| Crash after settlement / duplicate result                            | Settlement identity is unique per allocation/attempt. Reopen and fold durable records once; duplicate arrivals cannot charge twice or release a different reservation. Replay is non-executing and never calls adapters, clocks, reconciliation or grant issuers. Recovery is separately authorized, finite reconciliation.                                                                                                                                                                                                                    |
| Persistence fails, disk fills, torn tail or owner lost               | No dispatch unless a complete reservation is durable. A failed settlement retains the reservation and blocks new work; reopen/reconcile before continuation. A failed halt write still blocks in process and rejects explicitly, never reports a successfully persisted pause. Durable pre-call evidence must reconstruct the refusal/uncertainty after restart. Corrupt interior records fail closed; only a provably incomplete final record is repairable.                                                                                  |
| Cancellation before admission or during pacing/quota/allocation wait | No invocation. Release only a proven unstarted allocation through durable evidence; cancel waiters. Recheck after every await. A started invocation count is never refunded.                                                                                                                                                                                                                                                                                                                                                                   |
| Cancellation mid-invoke / late usage                                 | Request abort/process termination through existing ports; no next attempt. Retain the full reservation until a terminal/uncertain settlement. Reuse adapter `settle_on_abort` / `await_on_abort` contracts and injected Timer; late results may settle the same liability once but cannot restart work. Cancellation does not imply zero cost or undo effects. Preserve host effect holds until reconciliation.                                                                                                                                |
| Resume after a halt, including two racing resumes                    | Verify entitled principal, halt ID, goal/cycle, policy revision and amendment. Atomically append consumption of a unique resume authorization together with the transition out of that halt; then issue fresh execution grants as needed. Consumption survives crash before dispatch, expiry and replay. A consumed authorization can be inspected but never used again; another interruption needs a fresh one. A grant copied from a journal is not reissued. Resume rechecks quota, D4/D7, permissions, uncertainty and remaining counters. |

Use one durable stream for the authoritative reservation, halt and resume state
so a multi-file partial commit cannot create spend authority. Existing attempt,
audit and host journals may cite that stream; their projections do not decide
resource availability. Before enabling enforcement, strengthen the chosen
observation-journal implementation to append-and-sync before return, sync file
creation, recover torn tails, enforce exclusive ownership and preserve
deduplication/revision checks. `FileAttemptJournal` offers a local durability
precedent; reuse it by composition where suitable, without pretending its
single-writer detection is a cross-process lock. Do not import Fabric storage
into Loom or build a general distributed ledger for this issue.

Single-use resume authorization is proposed authority state, distinct from the
current `resume:true` flag, a `ResumePoint`, and a capability execution grant.
Persist consumption even if a subsequent provider call fails. Retrying the same
resume request may return its recorded receipt, but may not start a second
continuation. Terminal stops cannot resume; new goal authority must be explicit.

## Benchmark isolation and shadow traffic

Install production accounting and guardrail composition explicitly. Do not add
ambient wrappers, adapter-global middleware or option shuffles. Preserve
`buildProviders` direct benchmark calls (including the opt-in `nous-portal`
adapter call), `buildCompetitors` and the explicit Muse Spark competitor
configuration, `createJevGateway` / `createKevGateway` construction, Jev reference
pins and `shuffle:false`. A benchmark's explicit budget may refuse a dispatch, but
must record incompleteness rather than switch models, change questions/order,
inject D4/D7 prompts or relabel results. Normal production privacy checks
continue to apply on production routes.

No shadow dispatcher was found at HEAD. If introduced, every paid shadow attempt,
retry and failed/cancelled result needs its own durable allocation, marked as
shadow and linked to the triggering goal/cycle. Count it once in that goal's
total provider cost/tokens/invokes and in an explicit tighter experiment
suballocation; subtotals are views, not duplicate charges. Admit foreground
reservations first, refuse shadow work when allowance is unavailable, and never
let shadow output affect authority or completion. Out-of-goal experiments need
their own explicit budget and attribution; they cannot hide goal-triggered cost.

Before comparative runs, reserve adversarial/held-out cases independent of the
implementer. Do not use implementer-authored examples as sole quality evidence.
No benchmark run or hosted inference is needed for this plan. Any future hosted
run must first record data provenance/license, exact destination and sanitization
or explicit authorization under AGENTS.md. Keys enter through injected secret
ports/environment allowlists; never argv, logs, halt records or benchmark output.
