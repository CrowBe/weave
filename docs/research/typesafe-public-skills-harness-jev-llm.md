# TypeSafe's public skill: Jev and LLMs inside an agent harness

Research date: 2026-09-30; repository comparison refreshed against `4e9ebaf` on 2026-10-27. The original skill and documentation links were not revision-pinned; treat descriptions of the release as historical, and consult the linked live sources for current details. Scope: TypeSafe's public [`typesafe-ai/skills`](https://github.com/typesafe-ai/skills) release, its linked first-party documentation and cookbooks, and the adjacent first-party System One adapter. This is source analysis, not a benchmark or an implementation proposal.

## Main finding

The public repository presented one installable `typesafe-ai` skill. It instructs a coding agent to **build software that calls** TypeSafe's System One API; it does not turn the coding agent itself into a Jev agent. The skill's central division is: code owns the workflow, Jev supplies narrow typed judgments and probabilities, and an ordinary LLM remains available for generation or harder reasoning. TypeSafe's [coding-agent guide](https://docs.typesafe.ai/introduction/coding-agents) explicitly says Jev cannot replace the chat/code-completion model behind Claude Code or Codex. [Repository README](https://github.com/typesafe-ai/skills/blob/main/README.md), [skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), [coding-agent guide](https://docs.typesafe.ai/introduction/coding-agents).

This is best read as a **harness composition pattern**, not a claim that Jev should govern an autonomous loop. The skill says to keep known rules, calculations, exact lookups, and execution in code; ask bounded semantic questions; then let code use answers to select, verify, route, or escalate. Its stateful pattern says code retains goals and observations while fresh judgments guide the next bounded step, with inferred state distinguished from observed facts and freshness checked before applying an answer. [Skill, “Find the useful shape” and “Compose and verify”](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md).

## How the harness coordinates Jev and LLM inference

1. **Construct a state view and bounded question set.** The skill asks for relevant source text, identities, relationships, policies, and current facts. It says instructions carry the judgment's meaning, criteria define possible answers, and code-facing question IDs are not sent to the model. In that assessment, `Choice` selected from a defined set, `Noul` gave a yes probability, and `Score` evaluated an ordered dimension. The live skill now also describes `Box` for image locations; this note did not assess that primitive. Include a no-match outcome when none of the offered candidates may fit. [Skill, “Design the judgments”](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), [System One](https://docs.typesafe.ai/concepts/system-one).
2. **Batch independent judgments; stage dependent work.** The skill says independent questions over the same state can be asked together, including speculative questions whose results code may ignore. They cannot see each other's answers. Make another request when an earlier answer is needed to fetch evidence, build new state, or determine the next candidates. This is a specific dependency boundary, not a general instruction to serialize every judgment. [Skill, “Compose and verify”](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), [speculative fan-out](https://docs.typesafe.ai/patterns/fan-out).
3. **Choose the next branch in code.** TypeSafe's intent-routing example classifies intent and complexity, then branches to deterministic order-status handling, one of several specialist LLMs, or a human. The Jev answer supplies a signal; the application names handlers and decides which one runs. [Intent routing](https://docs.typesafe.ai/patterns/intent-routing).
4. **Use LLMs for generation and reasoning where needed.** A RAG cookbook filters and labels retrieved passages with Jev before a Claude model writes the answer. Its extraction cascade runs a small text LLM, asks Jev field-level verification questions, and invokes a stronger reasoning LLM only when the verifier gate fires. [RAG passage classification](https://docs.typesafe.ai/cookbooks/classifying_rag_passages), [SDE cascade](https://docs.typesafe.ai/cookbooks/sde_cascade).
5. **Check the LLM's output when the task needs it.** The skill suggests checking claims or fields against evidence and escalating failing or uncertain results to a person or reasoning model. The guardrails cookbook screens messages on both sides of an LLM using several narrow hazard judgments; named code policy maps raw probabilities and severity to pass, review, block, or support. [Skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), [guardrails cookbook](https://docs.typesafe.ai/cookbooks/llm_guardrails).

The implied control flow is:

```text
observed state + available candidates + policy
                  │
        Jev typed judgments
                  │
       validate and compose in code
          ├─ deterministic handler
          ├─ specialist or stronger LLM
          ├─ human / more evidence
          └─ bounded action, if policy admits it
                  │
          observe result; rebuild state
```

That diagram is a synthesis of the [skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), [intent-routing pattern](https://docs.typesafe.ai/patterns/intent-routing), and [System One workflow](https://docs.typesafe.ai/concepts/system-one), rather than a diagram TypeSafe publishes verbatim.

These examples show both **Jev before LLM inference** (handler routing, retrieval selection, input screening), **Jev after LLM inference** (field verification, output screening), and **Jev as a hint to an LLM agent** (skill suggestion). The claim that this is a reusable orchestration pattern is an inference from the cited examples, not a measured universal improvement.

## Authority, uncertainty, and evidence limits

The skill's strongest authority statement is that typed output guarantees an interface, not truth. It says to keep policy explicit, preserve raw judgments for reuse, evaluate thresholds on the user's data and consequences, and test representative cases plus resulting application behavior. It also distinguishes missing evidence, model errors, code errors, and service failures when debugging. [Skill, “Compose and verify”](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md).

`Choice` and `Score` confidence summarize concentration of an answer distribution. It is not overall workflow correctness or permission to act. `Noul` has a yes probability but no separate confidence field. TypeSafe describes its models as trained for calibrated decisions while warning that group-level calibration does not guarantee a particular answer is correct. The skill asks for target-domain validation; the confidence guide says thresholds depend on stakes and observed performance. [Skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), [confidence](https://docs.typesafe.ai/confidence), [System One](https://docs.typesafe.ai/concepts/system-one).

The published numeric thresholds and cookbook results are examples. In particular, the skill-suggestion experiment used a pinned Jev version and a pinned Claude model; its covered requests were generated from each skill's own instructions, and the page itself says this makes them easier than real user requests. The 100-prompt extraction cascade is explicitly described as internal TypeSafe results and a historical cost snapshot. These reports support the _shape_ of the harness but do not prove gains on Weave tasks. [Skill suggestion, setup and data](https://docs.typesafe.ai/cookbooks/skill_suggestion), [SDE cascade, 100-prompt section](https://docs.typesafe.ai/cookbooks/sde_cascade), [skill caution on demo thresholds](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md).

The skill does **not** specify an action-frontier scheduler, persistence format, cancellation policy, permission system, model-pool router, or admission gate for new capabilities. That is a bounded finding about the [one published skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), not a claim about all TypeSafe products. Its adjacent [adapter](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/README.md) is a way to compare LLMs through a common typed interface, not an instruction to give either model executive authority.

## Reading this against Weave

Related published notes cover [TypeSafe harness lessons](typesafe-harness-lessons.md) and the [System One adapter](typesafe-system-one-adapter-weave-decision-sites.md); those are separate analyses, not implementation evidence for this note.

The overlap with Weave is the separation of **judgment site**, **state view**, and deterministic execution. TypeSafe's skill supports asking semantic questions over a bounded state and treating answers as inputs to code. Weave's [VISION.md](../../VISION.md) goes further by explicitly making the runtime the agent, model output an observation, policy deterministic, and execution authority separate from inference. The [GLOSSARY.md](../../GLOSSARY.md) vocabulary calls the selected inference configuration a **routed unit**, the bounded question a **judgment site**, and validated executable possibilities **action candidates**. Jev should therefore be one possible routed unit at an evaluated judgment site; TypeSafe's examples do not establish that its sample thresholds should determine a Weave action frontier.

The Weave gateway at `4e9ebaf` separates `generate` and `evaluate`; an evaluation request has one answer shape (`choice`, `score`, or `boolean`) across its named questions. TypeSafe's skill and speculative fan-out example discuss batching independent questions, including different primitive types, in one System One call. Porting that batching pattern into Weave would require a deliberate contract change or separate gateway calls. It does not follow automatically from adopting the skill. [Weave gateway types](../../packages/gateway/src/types.ts), [TypeSafe skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md), [speculative fan-out](https://docs.typesafe.ai/patterns/fan-out).

A possible investigation, if this becomes implementation work, is a thin paired evaluation of one named Weave judgment site: freeze its state view, candidate set, policy, and outcome labels; compare Jev, a suitable LLM routed unit, and deterministic baseline on identical cases; measure error, uncertainty/escalation, latency, and total cost. This is a Weave-specific inference from TypeSafe's [test-on-your-data instruction](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md) and Weave's [VISION.md](../../VISION.md), not a TypeSafe recipe or a claim that Jev will win.
