# Contrastive Language Model (CLM): release and local-fit notes

Checked 2026-09-25. This is a source review, not a local CLM run. The author credits **Jacky Kwok** (spelled *Jacky* in the project's citation and package metadata), with Hangoo Kang, Tarun Suresh, Jon Saad-Falcon, Marco Pavone, Christopher Ré, and Azalia Mirhoseini. The project cites a [Notion blog](https://contrastive-lm.notion.site) rather than an archival paper; the accessible [author repository](https://github.com/Contrastive-LM/CLM) and [model card](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B) are the primary sources used here.

The 75.6 MB file is **not a standalone 20M-parameter model**: the [model card's encoder-locked limitation](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B#limitations) says its heads require Qwen3-8B last-token-pooled embeddings. The released runnable combination is an 8B encoder plus heads. I found no smaller checkpoint from this project in the [official model card](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B) or [author repository](https://github.com/Contrastive-LM/CLM); this is a review of published options, not proof that one cannot appear later.

The CLM code, its weights, and Qwen3-8B all state [Apache 2.0](https://github.com/Contrastive-LM/CLM#license) or [Apache 2.0](https://huggingface.co/Qwen/Qwen3-8B) licenses. The authors report a contrastive training sequence of about 60M Q&A pairs, 30M hard negatives, and 1M agent trajectories in the [repository](https://github.com/Contrastive-LM/CLM#data-recipe). These are author-reported training details, not independently verified here.

## Inference contract and runtime

CLM embeds a state and candidate actions separately, scores their alignment, and can reuse candidate embeddings. Its API supports typed [`noul`, `choice`, and `score` questions](https://github.com/Contrastive-LM/CLM#post-v1systemone), plus direct [`/v1/rank`](https://github.com/Contrastive-LM/CLM#post-v1rank). It returns relative candidate probabilities; the [model card](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B#limitations) says it does not generate text. For Weave, this is potentially relevant to bounded judgment sites, particularly choices over reusable candidates. The outputs remain observations rather than authority under Weave's runtime contract.

The [published quickstart](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B#usage) runs a **vLLM Qwen3-8B pooling server** on port 8090 and `clm-serve` on port 8700. The model card uses `--max-model-len 2048` and `--gpu-memory-utilization 0.35`; the model repository's latest cited commit explicitly says that the 2048 limit helps vLLM fit a **24 GB GPU**. The [package metadata](https://github.com/Contrastive-LM/CLM/blob/main/pyproject.toml) makes vLLM optional for the Python client/server package, while the [requirements file](https://github.com/Contrastive-LM/CLM/blob/main/requirements.txt) says its all-in install pulls vLLM for Linux and NVIDIA GPU. `clm-serve --device cpu` places the **heads** on CPU; it does not replace the Qwen embedding endpoint. The official repo also provides a [mock playground](https://github.com/Contrastive-LM/CLM#directory-structure), which is not a model benchmark.

An external `/v1/embeddings` service can be supplied with `--emb-url`, so a CPU encoder implementation is possible in principle if it reproduces the required Qwen3-8B text preparation and last-token pooling. I found no documented, validated CPU encoder path or CPU latency result in the released repository or model card. Substituting another backbone or unrelated embeddings would break the published head's contract. A quantized encoder would likewise need embedding-fidelity checks before treating the result as the released CLM; neither source reports such a check.

The authors report up to 9× lower latency than Jev on selected zero-shot tasks and strong fine-tuned verifier results. The [repository's evaluation section](https://github.com/Contrastive-LM/CLM#results) says those verifier numbers are from task-specific tuned heads, and the [model card](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B#limitations) warns they do not describe the zero-shot release. The reported latency uses GPU hardware and caching, so it must not be projected onto a CPU-only host without measurement.

## Practical local-fit conclusion

On this host, `lscpu` reports an Intel Core i7-1355U with 12 logical CPUs, `lspci` reports integrated Intel Iris Xe graphics, and the installed CPU PyTorch reports `torch.cuda.is_available() == False`. At the time of inspection, `free -h` showed **31 GiB total RAM and 22 GiB available**; `df -h .` showed **806 GB available disk**. These are local observations from 2026-09-25, not model measurements.

The encoder's [published configuration](https://huggingface.co/Qwen/Qwen3-8B/raw/main/config.json) specifies BF16. Its 16.4 GB published files are about 15.3 GiB before runtime overhead, while FP32 weights would be roughly twice that size. Disk is ample and a carefully loaded BF16 CPU process **might** fit the available RAM, but there is limited headroom for the embedding service, activation memory, caches, and other work. The official GPU vLLM command cannot run as written on this host. A faithful CPU `/v1/embeddings` service would be extra engineering; no full CLM request, peak RSS, or latency has been measured here.

**Decision for now:** CLM is relevant to bounded candidate ranking and typed judgment, but it is not a small local alternative to GLiNER2.5-Decide. Keep the GLiNER work. If CLM becomes a priority, use a suitable GPU host for a direct benchmark; otherwise first validate a CPU embedding implementation against the published Qwen3-8B last-token recipe, then measure full-request quality and latency on fresh `capability.match` and `result.evaluate` cases. Do not interpret a head-only CPU smoke test as a full CLM run.
