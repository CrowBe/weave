# Lumma-Fev 4B and 9B for Weave judgment sites

Research date: 2026-09-28. Source review only: no checkpoint was downloaded, run, fine-tuned, or measured on Weave cases.

## Finding

FrontiersMind has published both [`Lumma-fev-4b`](https://huggingface.co/FrontiersMind/Lumma-fev-4b) and [`Lumma-fev-9b`](https://huggingface.co/FrontiersMind/Lumma-fev-9b), linked from its [official decision-model collection](https://huggingface.co/collections/FrontiersMind/lumma-decision-models). The earlier 0.6B card calls the latter “Lumma-feb-9B”; the released repository spells it `fev`. Both are open-weight, Apache-2.0 decision models with custom inference code, rather than chat models coerced into Jev-shaped JSON. The 9B name is approximate: Hugging Face displays 8B parameters on its [model page](https://huggingface.co/FrontiersMind/Lumma-fev-9b).

The models are relevant to Weave's typed **judgment sites**, but published results do not justify routing one today. On the publisher's own `Typed-decisions` row, 4B scores **0.48**, 9B **0.49**, and Jev 1.13.0 **0.72**. The same cards report higher Lumma scores on AG News, DAIR Emotion, and Banking77. These are publisher-reported numbers; the cards do not give per-task sample counts, split/contamination details, uncertainty intervals, or a reproducible evaluation command. A mean across these datasets is therefore not a Weave decision-quality estimate. [4B card](https://huggingface.co/FrontiersMind/Lumma-fev-4b), [9B card](https://huggingface.co/FrontiersMind/Lumma-fev-9b).

## What is available

| Surface | Verified evidence | Consequence |
| --- | --- | --- |
| Checkpoints and license | The [4B file tree](https://huggingface.co/FrontiersMind/Lumma-fev-4b/tree/main) lists an 8.42 GB safetensors file; the [9B tree](https://huggingface.co/FrontiersMind/Lumma-fev-9b/tree/main) lists 15.9 GB. Both include model/config/backbone Python files, `LICENSE`, and `NOTICE`, and their cards declare Apache-2.0. | These are full checkpoints that can be independently inspected and served. Pin a commit before comparison. |
| Native decision shape | The [model code](https://huggingface.co/FrontiersMind/Lumma-fev-4b/blob/main/modeling_fev.py) packs one state with each question into a causal row, reads option states through a pointer head, and softmaxes over options. It accepts `noul`, `choice`, and ordered `score` with 1–255 options for the latter two. It produces distributions without generating text. | Shape compatibility is native, not a schema/retry wrapper. It still says nothing about site-specific semantic correctness or calibration. |
| API | The [publisher's `lumma-fev` PyPI package](https://pypi.org/project/lumma-fev/) supplies local loading, a client, and `lumma-fev-serve` with `POST /v1/systemone`; the package says a TypeSafe SDK client can use that endpoint. It reports that requests run one at a time. | A separate serving process could be tested behind Weave's existing inference gateway. Verify the actual protocol boundary and concurrency before integration. |
| Training | The 4B card says it was continually pretrained and fine-tuned on Qwen 3.5 4B. The 9B card repeats the same 4B sentence; both [4B config](https://huggingface.co/FrontiersMind/Lumma-fev-4b/blob/main/config.json) and [9B config](https://huggingface.co/FrontiersMind/Lumma-fev-9b/blob/main/config.json) have empty `base_model_name_or_path` and `base_revision`. The published model trees and PyPI package show inference artifacts, not a documented training recipe. | Open weights permit studying a fine-tune, but a reproducible site-specific fine-tuning procedure and exact base lineage are not established by this release. Ask the publisher for training code/data format or develop and validate a separate recipe. |

The [inference code](https://huggingface.co/FrontiersMind/Lumma-fev-4b/blob/main/modeling_fev.py) caps a state/question row at 8,192 tokens, truncates state text at its limit, and raises an error when the remaining question does not fit. It batches question rows within a 16,384-token pass budget; larger requests use several passes. The publisher's “single forward pass” description therefore applies only when the request fits that budget. For Weave, record the actual state-view manifest and any truncation as part of the routed unit's evidence; do not silently present a partial view as the full state.

## Fit on the current 32 GB CPU host

The [package documentation](https://pypi.org/project/lumma-fev/) says it loads bf16 on accelerators and fp32 on CPU. Merely converting the published weights to fp32 suggests roughly **16.8 GB for 4B** and **31.8 GB for 9B**, before activations, tokenizer, Python/PyTorch, the operating system, and Weave. These are estimates from checkpoint size, not measured peak resident memory. The 9B path is therefore a poor fit for a 32 GB CPU-only host without a separately demonstrated lower-memory runtime. The existing [local OpenJev CPU probe](../../benchmarks/inference/openjev/README.md) found fp32 faster than bf16 on this machine but at much greater peak RSS; it does not measure Lumma. No CPU latency claim from the model cards can be transferred to this host.

## Weave experiment boundary

`VISION.md` keeps probabilistic judgment within deterministic policy, and `CONTEXT.md` gives each **judgment site** a typed input/output and its own evaluation history. Lumma's direct `choice` and `score` answers map naturally to proposed `capability.match` and `result.evaluate` sites in the [Jev benchmark plan](../../benchmarks/inference/jev/README.md). The first test should be `capability.match`: a frozen state view and versioned option set, including genuine `none`/`unknown` cases. Then test `result.evaluate` only with independent outcome labels and an explicit ordinal rubric. Neither a valid probability map nor a publisher benchmark grants execution authority.

Use the [existing adapter investigation](typesafe-system-one-adapter-weave-decision-sites.md) as the comparison protocol: same protected cases and byte-identical views for base/current route, Jev, Lumma 4B, and, only on suitable hardware, Lumma 9B. Measure structural validity, semantic accuracy against constant predictors, option-order and evidence-change sensitivity, abstention, calibration, full-request latency, peak RAM, and serial-serving throughput. Preserve raw probabilities and model/revision/dtype/settings; set thresholds on a calibration split and report protected results separately. A site-specific fine-tune needs its own independent training and protected evaluation data. Keep the server outside Weave's runtime and admit only a site/version combination that clears predeclared quality and resource gates.

**Practical judgment:** 4B is worth a bounded offline probe after the source and hardware checks; 9B should wait for suitable hardware or a verified memory-saving implementation. The publisher's own `Typed-decisions` row makes neither a presumed Jev replacement, and the release does not yet provide the fine-tuning recipe needed to promise semantic-contract adherence.
