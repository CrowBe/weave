# TypeSafe's System One adapter for Weave judgment sites

Research date: 2026-09-28. This is an investigation and an experiment proposal, not an admitted route or a change to Weave's runtime contract.

## Finding

TypeSafe AI published [`typesafe-ai/system-one-adapter-python`](https://github.com/typesafe-ai/system-one-adapter-python). Its stated purpose is a drop-in replacement for the Python SDK's `system_one` evaluation API, backed by ordinary LLM APIs, so callers can compare a TypeSafe model with an LLM on cost, speed, and intelligence. The repository declares an MIT license, Python >=3.10, `typesafe-sdk>=0.7.0`, and version `0.2.1` in its [package metadata](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/pyproject.toml). This is an API compatibility adapter, not published Jev weights or a fine-tuning recipe. The [README](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/README.md) describes provider calls and answer conversion; its repository tree and package metadata do not expose a training pipeline. That is a finding about this release, not a claim that TypeSafe offers no training elsewhere.

The phrase “makes any model stick to the Jev input/output contract” needs a narrow reading. It can request a valid *shape* from a supported chat provider, parse it, retry malformed output, and return SDK-compatible answer objects. It cannot, by schema alone, make an arbitrary model understand a judgment site's meaning, preserve uncertainty, or emit calibrated probabilities. The adapter's own `llm_answer_mode` distinguishes discrete answers from model-stated probabilities, and `normalize_probabilities` can rescale distributions. A syntactically valid answer can still be wrong. [README](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/README.md), [schema builder](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/src/system_one_adapter/_schema.py), [answer conversion](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/src/system_one_adapter/_client.py).

## What the release actually supplies

| Surface | Verified behavior | Consequence for Weave |
| --- | --- | --- |
| Input | A `state` plus named `Noul`, `Choice`, or `Score` questions, matching the Python SDK's question vocabulary. `Choice` and `Score` must have at least two criteria in this adapter. [README](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/README.md), [schema builder](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/src/system_one_adapter/_schema.py) | Weave's `boolean` maps to TypeSafe's `noul`; this translation already exists in [`packages/gateway/src/adapters/typesafe-ai.ts`](../../packages/gateway/src/adapters/typesafe-ai.ts). |
| Provider | Optional OpenAI-compatible, Anthropic, and Gemini providers; custom OpenAI-compatible endpoints can be supplied through an `OpenAIProvider`. Both sync and async clients exist. [README](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/README.md) | A fine-tuned model is reachable only if a provider can serve it through a compatible chat interface. “Any model” is not a tested compatibility guarantee. |
| Output shape | For each request it builds a strict Pydantic model and JSON schema with exact question IDs and allowed labels; extra fields are forbidden. It supports native structured output or prompted JSON, then validates locally. [schema builder](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/src/system_one_adapter/_schema.py), [README](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/README.md) | Useful as a conformance reference for closed labels, missing answers, and malformed payloads. Provider structured mode may omit schema constraints, so local validation remains necessary. |
| Conversion | In discrete mode, `Noul` becomes 0 or 1, while `Choice` and `Score` become distributions derived from the selected option. In probability mode, the model is asked for probability values; `Score` becomes an expected rubric level, `Choice` takes the maximum, and confidence is computed from the distribution. [answer conversion](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/src/system_one_adapter/_client.py) | The API fields are synthesized. Neither normalization nor derived confidence demonstrates statistical calibration. Keep raw model output and conversion metadata. |
| Failures and receipts | It distinguishes malformed-output retries from transient provider retries and records attempts, request parameters, provider responses, retry reasons, token totals, and latency. Terminal errors retain attempts. [README](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/README.md), [response type](https://github.com/typesafe-ai/system-one-adapter-python/blob/main/src/system_one_adapter/_response.py) | This can support reproducible offline evaluation, with appropriate state and privacy controls. Retries must count toward total latency and cost. |

The official [Python SDK models](https://github.com/typesafe-ai/typesafe-sdk-python/blob/main/src/typesafe_sdk/_schemas/models.py) define `Noul` as a yes probability; `Choice` includes selected label and per-label probabilities; `Score` includes a probability-weighted expected level, level probabilities, legend, and confidence. Matching those fields is *protocol adherence*. It is not evidence that a model's decisions satisfy a Weave judgment site's semantic contract.

## Fit with Weave

`GLOSSARY.md` defines a **judgment site** as a named bounded question with typed input/output and its own evaluation history; a **routed unit** includes the context profile, prompt version, model, and settings. `VISION.md` gives model output the status of an observation, while deterministic policy controls authority. Existing gateway types distinguish `choice`, `score`, and `boolean`; the direct TypeSafe adapter already translates `boolean`/`noul`. [`benchmarks/inference/jev/README.md`](../../benchmarks/inference/jev/README.md) proposes `capability.match` (`choice`) and `result.evaluate` (`score`) and describes `frontier.weigh` as score-shaped. These are candidates and experiments, not evidence that a dedicated model is admitted. The current decision layer weighs a policy-bounded action frontier; a fine-tune must never turn a weight into an execution grant.

The useful extension is therefore at the **inference gateway**, preserving the existing Weave request/result types. A separate model-serving process may host a base model plus a site-specific fine-tune. A Weave adapter can send a versioned state view and closed question to that process and validate the returned answer. The TypeSafe package is Python and returns Python SDK objects; Weave's gateway is TypeScript. Replacing Weave's gateway with the package would introduce an unnecessary runtime dependency. Port only proven conformance rules or use the package in an isolated Python comparator. This is a design inference from the package and current repository boundaries, not a capability the published adapter claims to provide.

## Smallest useful experiment

1. **Choose one site and freeze its contract.** Start with `capability.match`, since it is a closed choice over established capability/composition candidates and permits an explicit `none` or `unknown` arm. Record site ID, decision shape, state-view/context-profile version, question/rubric version, candidate-set rules, and the exact semantic success condition. `frontier.weigh` is higher-volume but score labels and downstream outcomes are harder to adjudicate; `result.evaluate` should wait until partial-success and completion labels are reliable. This ordering is a proposal, not an observed performance claim.
2. **Collect independent labels.** Use real Weave traces where disclosure is authorized; label from human adjudication or observed outcomes, not from Jev responses. Include hard near misses: semantically adjacent capabilities, missing inputs, a needed composition, and true `none`/`unknown`. Keep training, tuning/validation, calibration, and protected promotion cases disjoint by task family/source and time where possible. Existing synthetic GLiNER pilots are feasibility evidence only; they cannot establish production routing quality.
3. **Measure three distinct gates.** (a) Structural conformance: exact IDs/labels, full probability map where requested, numeric bounds, finite values, sum tolerance, malformed/refusal handling, cancellation, and retry accounting. (b) Site semantics: accuracy or ordinal/ranking loss against labels, class floors, contrast pairs, changed evidence, option order, abstention, and false-positive cost. (c) Calibration and routing: reliability/Brier or ECE by site and class, threshold coverage/error curves, and paired end-to-end cost including retries and escalation. Passing (a) does not imply (b) or (c).
4. **Compare on identical cases.** Run base model, fine-tuned model, TypeSafe Jev, and Weave's current strong route against the same frozen state views. Record raw outputs and conversion settings. Prefer direct closed-label logits or discrete labels if the serving model supports them; treat the published adapter's generated probability maps as uncalibrated until independent calibration passes. Do not fit thresholds or calibrators on the protected comparison set.
5. **Promote narrowly if earned.** Admit only the versioned site + shape + state-view/rubric + model/settings combination that meets predeclared quality, abstention, latency, memory, privacy, and total-cost gates. Keep the gateway's deterministic routing and escalation, replay evidence, and rollback target. No generic “Jev-compatible” route follows from one successful site.

## Open questions for a technical spike

- Can the intended fine-tune's serving stack expose the exact question/answer protocol directly, or only a chat endpoint that needs schema prompting and retries?
- Does its training target predict a discrete class, a ranking/ordinal level, or a distribution? Those are different learning problems even when they serialize to the same TypeSafe answer object.
- What independent `capability.match` corpus is available, with permission to use it for training and retained protected evaluation? How many genuine `none`/`unknown` cases does it contain?
- Which model/base and serving route meet the actual hardware, privacy, latency, and peak-RAM envelope? The adapter itself supplies no evidence for any particular fine-tune's quality or operational fit.
